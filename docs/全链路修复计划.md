## 一、问题全景图

### 1.1 根本原因（一句话）

**ultralytics NCNN 导出自动将完整后处理（DFL 解码 + 锚点计算 + sigmoid）嵌入模型图，导致 C++ 推理代码对其执行双重后处理。**

### 1.2 影响范围

| 场景 | 是否受影响 |
|------|-----------|
| 内置 COCO 模型（三输出 raw DFL） | ❌ 不受影响 |
| ultralytics 导出自训练模型（单输出 decoded） | ✅ 完全不可用 |

### 1.3 数据流对比

```
【内置模型路径】(正常)
  model.param → out0[64+nc,H,W] + out1[64+nc,H,W] + out2[64+nc,H,W]
  → C++ generate_proposals() DFL解码 → sigmoid → NMS → 正确结果

【ultralytics 导出路径】(异常)
  model.param → out0[5,8400]（DFL+sigmoid已在图内完成）
  → C++ generate_proposals() 再次DFL解码 → 再次sigmoid → 错误结果
```

## 三、待验证/待修复项

### 🔴 V1: generate_proposals decoded 坐标是否需要再乘 stride
**问题**: ultralytics 导出的坐标可能是归一化 [0,1] 值，而 Mill 的代码中直接用 cx, cy, w, h 作为像素坐标  
**需确认**: 模型输出的实际坐标空间

**验证方法**:
```python
# 用 ultralytics 导出模型后，检查 MemoryData 锚点值
# 如果锚点值是归一化的（如 0.0005），则坐标需要 * target_size
# 如果锚点值是像素级的（如 0.4, 0.8），则坐标直接可用
```

**可能需要的修复**: 如果坐标是归一化的，需要在 generate_proposals 中乘以 target_size

### 🔴 V2: NMS 中的坐标变换兼容性
**问题**: `non_max_suppression()` 中的 `scale_unpad` 假设坐标是模型输入空间（target_size × target_size）的像素坐标  
**需确认**: decoded 格式的坐标经过 scale_unpad 后是否正确映射到原图

### 🟡 V3: draw() 函数坐标格式
**问题**: `draw()` 直接使用 `obj.rect` 绘制，rect 应为左上角坐标  
**需确认**: decoded 格式下 rect 的 x,y 确实是左上角（cx - w/2, cy - h/2）

### 🟡 V4: Kotlin labels 与 C++ labels 一致性
**问题**: Kotlin `loadLabels()` 和 C++ `loadLabelsFromPath()` 是独立加载的，可能加载到不同的标签集  
**风险**: 如果 Kotlin 加载 COCO 默认而 C++ 加载自定义标签，映射会错位

**建议**: 统一由 C++ 端加载标签并返回给 Kotlin，或确保两端使用同一路径

### 🟡 V5: export_pipeline.py 文档不准确
**问题**: 文档声称输出 `[class_id, confidence, x, y, w, h]`（归一化坐标），实际输出格式为 `[cx, cy, w, h, prob, 8400]`  
**修复**: 更新文档描述，说明 ultralytics NCNN 导出的实际格式

### 🟢 V6: 模型配置文件 nc 参数不一致
**问题**: `training/configs/models/yolo11-se.yaml` 等文件中 `nc=80`，但实际训练自定义数据集时 nc 不同  
**影响**: 训练脚本会通过 CLI 参数覆盖，但如果直接使用 yaml 可能出错

### 🟢 V7: export_pipeline 缺少输出格式验证
**建议**: 导出后检查 model.param 的输出层维度，警告用户格式差异
